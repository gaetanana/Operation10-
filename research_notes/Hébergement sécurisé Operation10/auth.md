# Secure Authentication for a One-Owner React + NestJS + PostgreSQL App (Publicly Deployed)

Context: single owner/admin account, no public signup, provisioned secret/password. Comparing (A) server-managed session cookies, (B) short-lived JWT in browser storage, (C) identity-aware access gate at the hosting/proxy layer. All sources checked 2026-11-05.

## Session cookies vs. short-lived JWT in browser storage — which is safer for this app?

### Takeaway
For a traditional browser-based client talking to its own backend, OWASP's own guidance is to prefer server-side sessions identified by a cookie over storing bearer tokens (JWTs) in the browser; JWTs in browser storage are mainly justified for stateless, multi-service/mobile/SPA-to-third-party-API architectures, which this single-owner app does not need. A cookie-based session with `HttpOnly`, `Secure`, `SameSite` flags plus a CSRF defense is the "essential" choice; JWT-in-browser-storage with refresh-token rotation is "overkill" complexity for one user and introduces XSS-exfiltration risk that cookies avoid.

### Cited Findings
- OWASP's Session Management Cheat Sheet treats the authenticated session ID/token (commonly a cookie) as the baseline mechanism "temporarily equivalent to the strongest authentication method used by the application" and dedicates the whole cheat sheet to cookie-based session design (entropy, rotation, expiration) as the recommended approach — [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
- OWASP explicitly recommends cookies over URL parameters or other exchange mechanisms because cookies support attributes like expiration and usage constraints that other mechanisms lack, and warns that alternative mechanisms can leak the session identifier via browser history, logs, or the Referer header — [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
- OWASP's REST Security Cheat Sheet frames JWT/bearer-token access tokens as the pattern for **stateless, multi-service REST architectures** where "user authentication should be centralised in an Identity Provider (IdP), which issues access tokens," i.e., a different problem (service-to-service/microservices) than a single first-party app with its own backend — [OWASP REST Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html).
- OWASP's Session Management Cheat Sheet explicitly discusses the alternative of storing only a hashed "verifier" server-side (identifier + secret-verifier split) specifically so that disclosure of the session store alone doesn't compromise live sessions — this directly addresses the main theoretical advantage of JWTs (no server lookup) while keeping revocability, which opaque session cookies provide and client-stored JWTs do not — [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
- A cookie marked `HttpOnly` cannot be read by page JavaScript (mitigating token theft via XSS), whereas a JWT kept in `localStorage`/`sessionStorage` or in JS-accessible memory is fully readable by any script that runs on the page (XSS automatically becomes session theft) — [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
- NestJS ships first-class, zero-extra-package building blocks for a cookie+CSRF session model (`app.useSecurityHeaders()` for security headers, `app.enableCsrfProtection()` using Fetch-Metadata/Origin validation, `@nestjs/throttler` for rate limiting), showing the framework's own security docs are oriented around the cookie/CSRF model rather than JWT-in-storage — [NestJS CSRF Protection](https://docs.nestjs.com/security/csrf), [NestJS Security headers](https://docs.nestjs.com/security/helmet), [NestJS Rate Limiting](https://docs.nestjs.com/security/rate-limiting).
- OWASP's CSRF Prevention Cheat Sheet confirms the trade-off directly: cookie-based auth is vulnerable to CSRF (because the browser auto-attaches cookies) and therefore needs a CSRF defense (framework-provided token, Fetch Metadata headers, or SameSite), whereas token-based auth carried in a custom header (not auto-attached) is not CSRF-vulnerable by construction — but the cheat sheet still recommends layering `SameSite` on session cookies as a primary defense — [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

### Inferences
- For this project (single owner, first-party React SPA + first-party NestJS API, same registrable domain, no third-party API consumers, no mobile app, no microservices), none of the conditions that justify bearer JWTs (stateless horizontal scaling across many services, third-party API clients, mobile apps without cookie jars) apply. The “essential” choice is therefore a server-managed session identified by an `HttpOnly; Secure; SameSite=Strict` (or `Lax`) cookie, with NestJS's built-in Fetch-Metadata CSRF protection (or a `csurf`-style token if an older Nest version is used) as the CSRF defense.
- Short-lived JWTs in browser storage are "overkill/wrong tool" here: they add complexity (access+refresh token rotation, revocation lists to regain the cookie model's instant revocability, XSS-exposure risk) without adding value for a single-owner, same-origin app.
- If JWTs are still desired for some reason (e.g., reusing the same auth for a separate mobile client later), OWASP's own cheat sheets imply the safer middle ground is to keep the JWT in an `HttpOnly` cookie (not `localStorage`) — this gets the CSRF/XSS trade-off of a normal session cookie while keeping a self-contained token if truly needed; but for this app, a plain opaque session ID is simpler and equally secure.

### Gaps
- OWASP cheat sheets do not give a single page titled "JWT vs cookie" with an explicit recommendation matrix; the comparison above is synthesized from the Session Management, CSRF, and REST Security cheat sheets, which is noted as inference rather than a single direct quote.
- Could not retrieve an OWASP "JSON Web Token Cheat Sheet" (URL guessed `JSON_Web_Token_for_Java_Cheat_Sheet.html` returned 404); the general JWT guidance used above comes from the REST Security Cheat Sheet's JWT section instead.

## Identity-aware access gate at the hosting/proxy level — should it replace or supplement app-level auth?

### Takeaway
An identity-aware proxy (e.g., Cloudflare Access/Zero Trust in front of the origin) is a legitimate **defense-in-depth** layer that can gate the entire public hostname behind an additional login (e.g., a one-time PIN or the owner's own IdP account) before traffic even reaches NestJS, but it should supplement — not replace — in-app authentication, since the task explicitly disallows prescribing an external identity provider unless needed and self-hosted single-owner apps can get equivalent protection more simply via network-level restriction (VPN/allow-list) or just a hardened in-app login.

### Cited Findings
- Cloudflare Access lets you "securely publish internal tools and applications by adding Cloudflare Access as an authentication layer between the end user and your origin server," enforcing an Allow/Block/Bypass policy per hostname, with "Access is deny by default -- a user must match an Allow policy before they are granted access" — [Cloudflare: Publish a self-hosted application to the Internet](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/).
- Cloudflare Access policies can gate by selectors such as email address, email domain, country, or device posture, and issue a short-lived "application token" cookie that Cloudflare checks on every HTTP request, re-prompting reauthentication with the identity provider when it expires — [Cloudflare Access Policies](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/) and [Self-hosted public app](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/).
- Cloudflare Access requires configuring at least one identity provider (IdP) to authenticate users (email domain, SSO, etc.) — i.e., this layer by design needs *some* identity source, even if it's just Cloudflare's own one-time-PIN email login rather than a full external IdP like Google/Okta — [Cloudflare Access Policies / self-hosted public app docs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/).

### Inferences
- Given the explicit constraint "do not prescribe an external identity provider unless needed," a full Cloudflare Access/Zero Trust gate is **optional hardening, not essential**, because it reintroduces a third-party identity dependency (even "email OTP" is Cloudflare acting as an IdP) for a single-owner app that can already be protected by a strong in-app password + rate limiting + session cookie.
- Where it *is* worth it: if the hosting provider/CDN in front of the app is already Cloudflare (common for small deployments) and the owner wants to prevent any unauthenticated request — including exploit probes against the login page itself — from ever reaching the NestJS process, Cloudflare Access (or a simpler reverse-proxy HTTP Basic-Auth gate, or an IP allow-list if the owner has a static IP) adds a cheap outer layer that reduces the app's exposed attack surface (fewer requests reach Node.js, including pre-auth bugs).
- A lighter-weight, non-IdP alternative achieving a similar "nobody but the owner can even reach the app" goal is restricting access at the network layer (hosting provider firewall / security group allow-listing the owner's IP, or putting the whole app behind a private network/VPN the owner controls) — this avoids any third-party identity dependency entirely, at the cost of the owner needing a stable way to reach the IP range (e.g., from multiple locations/devices) — this is an inference, not a direct citation, since no source above evaluates "IP allow-list vs. Access" trade-offs for this exact scenario.

### Gaps
- No OWASP cheat sheet specifically addresses "identity-aware proxy as defense in depth for a single-owner app"; this section relies on Cloudflare's own product documentation, which is authoritative for Cloudflare's product but is inherently vendor-specific, not a vendor-neutral standard.
- Did not find Cloudflare documentation directly discussing a non-IdP "shared secret" style gate (e.g., simple reverse-proxy Basic Auth) as a recommended alternative to Access; that option is inferred from general reverse-proxy capabilities, not sourced.

## Password storage, strength, and rotation for the single owner account

### Takeaway
Store the password using a slow, memory-hard hash (Argon2id preferred, bcrypt acceptable) with a per-user salt, enforce a strong minimum length rather than complex composition rules, and — per current NIST guidance that OWASP has adopted — do **not** force periodic password rotation on a timer; only rotate/change the password after a suspected compromise.

### Cited Findings
- OWASP's bottom-line recommendation: "Use Argon2id with a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism. If Argon2id is not available, use scrypt... For legacy systems using bcrypt, use a work factor of 10 or more and with a password limit of 72 bytes. If FIPS-140 compliance is required, use PBKDF2 with a work factor of 600,000 or more" — [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- "Passwords should never be stored in plain text... they must be protected using strong, slow hashing algorithms... A unique salt must be added to each password to prevent attackers from using precomputed lookup tables like rainbow tables. Fast hashing algorithms such as SHA-256 are not suitable for password storage" — [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- On password strength, OWASP cites NIST SP800-63B: "If MFA is enabled passwords shorter than 8 characters are considered to be weak... If MFA is not enabled passwords shorter than 15 characters are considered to be weak," and "Maximum password length should be at least 64 characters to allow passphrases," noting that length/blocklist checks are preferred over composition or entropy-math rules — [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) citing [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver).
- "Consider using a pepper to provide additional defense in depth (though alone, it provides no additional secure characteristics)" — i.e., a pepper (a secret stored outside the DB, e.g. in a secret manager/env var, combined with the hash) is a nice-to-have on top of hashing+salting, not a substitute for it — [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

### Inferences
- For a single-owner app, mandatory periodic rotation (e.g., "change password every 90 days") is **overkill** and current best practice (reflected in the NIST-aligned OWASP guidance above) discourages forced rotation in favor of long passphrases plus hashing strength; rotation should instead be **event-driven**: rotate immediately if compromise is suspected (leaked elsewhere, device lost, etc.).
- Essential: Argon2id (or bcrypt if the Node ecosystem library used is more mature/audited, e.g. `bcrypt`/`argon2` npm packages) with the parameters above, a unique per-record salt (most libraries generate this automatically), enforce a reasonably long passphrase (e.g., 15+ characters since MFA will likely not be present for a solo app, per the NIST thresholds cited), and a safety valve on max length to avoid "long password DoS" against slow hash functions.
- Overkill for one owner: building a full password-strength meter, blocklist-against-breach-corpus integration (e.g., Have I Been Pwned API) is "nice to have" but can be skipped initially given it's a single credential the owner controls; still worth a one-time manual check against a known breach list when first choosing the password.

### Gaps
- No pepper implementation guidance specific to Node/NestJS was fetched (only the general cheat-sheet statement that a pepper is optional defense-in-depth); if implemented, the pepper must be sourced from the same secret-management mechanism as other secrets (see Secrets section below).

## Session cookie flags and CSRF protection

### Takeaway
Set the session cookie with `HttpOnly`, `Secure`, and `SameSite=Strict` (or `Lax` if cross-site top-level navigation into the app is needed), use a high-entropy session identifier, and pair it with NestJS's built-in Fetch-Metadata CSRF protection (NestJS ≥ v12.1) or an explicit token-based CSRF defense on older versions; also store only a hashed verifier (or rely on a vetted session store) rather than a raw guessable session value.

### Cited Findings
- Cookie attribute semantics: `HttpOnly` "Forbids JavaScript from accessing the cookie... This mitigates attacks against cross-site scripting"; `Secure` restricts sending to HTTPS; `SameSite=Strict|Lax|None` controls cross-site sending, with `SameSite=None` requiring `Secure` — [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
- OWASP: session identifiers "must have at least 64 bits of entropy," generated via a CSPRNG, and recommends using the framework's own built-in session ID generator rather than a custom one, with at least 128 bits of entropy if generating one yourself — [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
- OWASP: "Storing random session tokens verbatim can be acceptable in a tightly controlled session store, but anyone who can read it can reuse unexpired tokens... If read-only disclosure of the store is in your threat model, store a one-way verifier instead" via an identifier+secret-verifier split, hashing the verifier (SHA-256) server-side and comparing in constant time — [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
- NestJS (v12.1+) provides `app.enableCsrfProtection()`, implementing a Fetch-Metadata-based defense modeled on Go 1.25's `net/http.CrossOriginProtection`: it allows `GET/HEAD/OPTIONS` always; for other methods it requires `Sec-Fetch-Site` to be `same-origin`/`none`, or (as a fallback for older browsers lacking that header) requires the `Origin` header's host to match the request's `Host` header; requests with neither header (non-browser clients) are allowed through — this needs **no extra cookie or client code change** — [NestJS CSRF Protection](https://docs.nestjs.com/security/csrf).
- OWASP's CSRF cheat sheet top-line guidance: check for built-in framework CSRF protection first; if none, add CSRF tokens (synchronizer token pattern for stateful apps) to all state-changing requests; `SameSite` can be used on session cookies as a mitigation but with the caveat "NOT set a cookie specifically for a domain" when subdomains aren't all trusted, since subdomain takeover could then read the cookie — [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
- Important caveat repeated by OWASP: "Cross-Site Scripting (XSS) can defeat all CSRF mitigation techniques" — CSRF tokens/SameSite do not substitute for XSS prevention (output encoding, CSP) — [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

### Inferences
- Essential for this app: `Set-Cookie: <session>; HttpOnly; Secure; SameSite=Lax` (or `Strict` since there's no legitimate reason for top-level cross-site navigation to need the session, given it's a personal app with no external referral links that must carry the session) + no `Domain` attribute (let it default host-only) + a reasonable `Max-Age`/`Expires` plus server-side idle/absolute timeout; combine with NestJS's `enableCsrfProtection()` for a zero-extra-dependency CSRF defense, since the app already is first-party/same-origin.
- Overkill: implementing a custom synchronizer-token CSRF scheme by hand when the Fetch-Metadata built-in (or a maintained `csurf`-equivalent) already covers it; manually rolling a session-ID generator instead of the framework/session-store's own CSPRNG-backed implementation.
- Store sessions server-side (e.g., Postgres-backed or Redis-backed session store) with only an opaque ID in the cookie — this both avoids the JWT revocation problem and lets the app apply the identifier+hashed-verifier pattern OWASP describes if the owner wants extra hardening against DB-only disclosure (lower priority for a single-owner app, but cheap to add if using something like `express-session` with a custom store, or a small custom "sessions" table with a hashed token column).

### Gaps
- Did not fetch Express's `express-session` or NestJS's `@nestjs/passport` session-strategy docs in depth; the above is based on OWASP's framework-agnostic guidance plus NestJS's own CSRF/cookie primitives. If `express-session` is used, its own README documents `cookie.secure`, `cookie.httpOnly`, `cookie.sameSite`, and store options — worth the implementer double-checking directly against that package's docs during implementation.

## Rate limiting / brute-force and credential-stuffing protection

### Takeaway
Apply per-IP and per-account rate limiting on the login endpoint (and password-reset endpoint) using NestJS's built-in `@nestjs/throttler`, and layer in account lockout/backoff; full MFA is the single most effective defense per Microsoft's analysis cited by OWASP, but for a one-user app, rate limiting + strong unique password + optional MFA is a reasonable, non-overkill baseline.

### Cited Findings
- "Multi-factor authentication (MFA) is by far the best defense against the majority of password-related attacks, including credential stuffing and password spraying, with analysis by Microsoft suggesting that it would have stopped 99.9% of account compromises" — [OWASP Credential Stuffing Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html) (citing Microsoft's "Your Pa$$word doesn't matter" analysis).
- OWASP distinguishes three related attacks needing similar defenses: brute force (many passwords vs. one account), credential stuffing (breached username/password pairs replayed), and password spraying (one weak password vs. many accounts) — [OWASP Credential Stuffing Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html).
- OWASP recommends defense-in-depth with volume metrics per defense ("each defense should generate volume metrics for use as a detective mechanism") since any single client-side defense (e.g., device fingerprinting) can be spoofed or bypassed — [OWASP Credential Stuffing Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html).
- NestJS's official rate-limiting docs show `@nestjs/throttler` configured via `ThrottlerModule.forRoot({ throttlers: [{ ttl, limit }] })` and bound globally via `{ provide: APP_GUARD, useClass: ThrottlerGuard }`, with per-route overrides via `@Throttle()` and exemptions via `@SkipThrottle()`; multiple named throttler tiers (e.g., 3/sec, 20/10sec, 100/min) can be combined — [NestJS Rate Limiting](https://docs.nestjs.com/security/rate-limiting).
- When behind a reverse proxy, NestJS's docs flag that you must configure `app.set('trust proxy', ...)` (Express) so the real client IP (from `X-Forwarded-For`) is used for throttling rather than the proxy's own IP — [NestJS Rate Limiting — Proxies](https://docs.nestjs.com/security/rate-limiting).

### Inferences
- Essential: a tight throttler rule specifically on `POST /auth/login` (e.g., ~5 attempts per minute per IP and/or per account identifier) plus a slightly looser global API throttle, using `@nestjs/throttler`; must configure `trust proxy` correctly if deployed behind any reverse proxy/CDN (Cloudflare, Nginx, etc.), otherwise all requests appear to come from the proxy's IP and rate limiting becomes ineffective or blocks everyone.
- Reasonable addition, not overkill: account-level exponential backoff/temporary lockout after N consecutive failures (even for a single account) to blunt brute force beyond the IP-rate-limit alone, plus logging/alerting (e.g., email the owner) on repeated failed logins — this doubles as the "detective mechanism" OWASP recommends.
- Overkill for a single-owner app: full bot-detection/device-fingerprinting stack, CAPTCHA farms, or geo-velocity/impossible-travel analytics — these make sense for multi-tenant consumer apps, not a personal app with one legitimate user. If the outer identity-aware proxy (Cloudflare Access, see above) is used, this also inherently blocks most brute-force traffic before it reaches the login endpoint at all, somewhat reducing the urgency of a very elaborate in-app anti-brute-force stack.
- MFA (e.g., TOTP) is the highest-leverage addition per the cited Microsoft/OWASP stat, and is "nice to have" rather than strictly essential only because the owner is a single highly-motivated, security-literate user who can instead rely on a strong unique passphrase + rate limiting + the proxy gate; MFA is still recommended as a relatively low-cost, high-value addition if the implementer has time.

### Gaps
- Did not verify NestJS throttler's default storage backend behavior across multiple server instances/process restarts (in-memory by default); if the app runs as a single instance this is fine, but a multi-instance deployment would need a shared store (e.g., Redis) for the throttler — this wasn't directly confirmed from the fetched docs and should be checked against `@nestjs/throttler`'s storage-adapter docs at implementation time.

## Login/account recovery for a single owner (no public signup)

### Takeaway
Because there is no email-based public signup flow to reuse, "forgot password" should be a deliberately narrow, side-channel-based recovery path (e.g., a pre-provisioned recovery mechanism known only to the owner) rather than a full self-service reset flow; OWASP's general forgot-password principles (constant-time/constant-response messaging, rate limiting, single-use expiring tokens, independent recovery evidence) still apply if any reset flow exists at all.

### Cited Findings
- OWASP's core forgot-password guidance: "Return a consistent message for both existent and non-existent accounts," "Ensure that the time taken for the user response message is uniform," "Use a side-channel to communicate the method to reset their password," use single-use, expiring, cryptographically random reset tokens, and "Do not make a change to the account until a valid token is presented, such as locking out the account" — [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
- On reset requests: rate-limit per-account, and "Implement protections against excessive automated submissions such as rate-limiting on a per-account basis, requiring a CAPTCHA, or other controls. Otherwise an attacker could make thousands of password reset requests per hour" — [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
- On completing a reset: "Don't automatically log the user in, as this introduces additional complexity... Ask the user if they want to invalidate all of their existing sessions, or invalidate the sessions automatically" — [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
- On recovering from suspected compromise specifically (not just forgetting a password): "Do not rely solely on recently added or changed recovery information. Use independent, previously established recovery evidence... Do not automatically restore superseded recovery addresses or phone numbers; they may have been replaced because they were lost or compromised," citing NIST's account-recovery events guidance — [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) citing [NIST SP 800-63B account recovery events](https://pages.nist.gov/800-63-4/sp800-63b/events/#recovery).

### Inferences
- For a single-owner app with no public signup, a full self-service "forgot password" HTTP flow is likely unnecessary attack surface (it's a classic source of vulnerabilities per OWASP, e.g. user enumeration, and every additional endpoint is additional code to secure). A simpler, equally secure alternative is an out-of-band recovery procedure the owner controls directly, e.g.: a documented manual process to reset the password hash directly via a database migration/admin CLI script run by the owner (who already has infra/server access), or a pre-generated one-time recovery code stored by the owner in a password manager at provisioning time (shown once, hashed like the password, single-use).
- If an in-app reset flow is built anyway (e.g., "email myself a reset link"), it must still follow the OWASP rules above: single-use expiring token, rate-limited, no account enumeration via timing/response differences, and require re-authentication rather than silent auto-login after reset.
- Essential: whatever recovery mechanism is chosen, invalidate all existing sessions on any password change/reset, and notify the owner (e.g., via a channel outside the app, like email) whenever the password or recovery secret is changed, so an attacker's password change doesn't go unnoticed.

### Gaps
- OWASP's cheat sheet is written for multi-user apps with email/SMS channels; it doesn't directly address the "I am the only user and have server/infra access" scenario, so the "use an admin CLI/DB script instead of a web reset flow" recommendation above is an inference tailored to this app's constraints, not a direct citation.

## Secret management (passwords, session/JWT signing secrets, DB credentials)

### Takeaway
Keep all secrets (DB password, session/cookie signing secret, any JWT signing key, SMTP/third-party API keys) out of source control and container images, inject them via environment variables or a dedicated secrets manager depending on the hosting platform, apply least-privilege access, and rotate them if ever exposed; for a small single-owner deployment, a managed secrets store is "nice to have," while environment-variable injection from the hosting platform's secret store is the realistic essential baseline.

### Cited Findings
- "There is a growing need for organizations to centralize the storage, provisioning, auditing, rotation and management of secrets to control access to secrets and prevent them from leaking" — general framing from [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html).
- Access control principle: "engineers should not have access to all secrets in the secrets management system, and the Least Privilege principle should be applied" — [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html).
- Automation principle: "it is better to limit or remove the human interaction with the actual secrets," via a secrets pipeline or dynamic/short-lived secrets with short lease durations, to reduce the surface area of credential reuse — [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html).
- Standardization principle: even a single centralized secrets solution typically needs its own root/management credentials secured in a *secondary* location — relevant if the owner picks any managed secret store, the store's own master credential still needs careful handling — [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html).

### Inferences
- Essential, low-friction baseline for this app given a `docker-compose.yml`-based deployment observed in the repo: never bake secrets into the Docker image or commit them to the repo; use a `.env` file excluded via `.gitignore` for local/dev, and the hosting platform's native secret/environment-variable injection (e.g., a VPS provider's "environment variables" UI, or Docker secrets / an orchestrator's secret store) for production; ensure Postgres credentials, the session cookie signing secret, and any JWT/pepper value are all distinct, high-entropy, and not reused across environments (dev vs prod).
- Overkill for a single developer/owner: deploying a full HashiCorp Vault / cloud KMS cluster with dynamic short-lived DB credentials purely for one person's app — the OWASP cheat sheet's "automation/dynamic secrets" advice is aimed at organizations with many services and engineers; for this app, a well-protected `.env`/platform secret store plus a personal password manager for the master values is proportionate.
- If the budget/time allows a small step up without full Vault complexity: many hosting platforms (Railway, Render, Fly.io, etc.) offer built-in encrypted environment-variable stores separate from the repo, which satisfies "centralize and don't hardcode" without operating new infrastructure.

### Gaps
- No platform-specific secret-store documentation was fetched (the repo's actual hosting target wasn't specified); the recommendation above is generic to any modern PaaS/VPS and should be adjusted to whichever concrete hosting provider is chosen.

## CORS configuration

### Takeaway
Since the React frontend and NestJS backend are a first-party pair, CORS should be locked down to the exact known origin(s) of the frontend (not a wildcard), with credentials explicitly enabled only if cross-origin cookie use is actually required; NestJS's `enableCors()` makes this straightforward but defaults differ by underlying HTTP adapter and must be set explicitly.

### Cited Findings
- NestJS: "To enable CORS, call the `enableCors()` method... takes an optional configuration object" whose options map to the Express `cors` package's configuration options (or Fastify's `@fastify/cors`); CORS can also be enabled via `NestFactory.create(AppModule, { cors: true })` — [NestJS CORS docs](https://docs.nestjs.com/security/cors).
- NestJS's two underlying platforms don't share defaults: "the Express cors package answers `GET,HEAD,PUT,PATCH,POST,DELETE`, while `@fastify/cors` answers only the CORS-safelisted methods: `GET,HEAD,POST`," meaning a cross-origin `PUT/PATCH/DELETE` is silently rejected at preflight on Fastify unless `methods` is listed explicitly — [NestJS CORS docs](https://docs.nestjs.com/security/cors).

### Inferences
- Essential: explicitly set `origin` to the frontend's exact production URL(s) (never `*` when cookies/credentials are used — wildcard origin combined with `credentials: true` is rejected by browsers anyway, and is bad practice regardless) and set `credentials: true` only because the app relies on a cookie-based session that must be sent cross-origin (this is required if frontend and backend are served from different subdomains/origins; not needed if served from the exact same origin, which removes the CORS requirement entirely).
- If the simplest architecture is chosen — serving the React build from the same origin/domain as the NestJS API (e.g., Nest serves the static build, or both sit behind the same reverse-proxy host) — CORS can be avoided almost entirely, which is both simpler and reduces attack surface; this is the "essential, simplest" option. Running frontend and backend on different subdomains and configuring CORS+credentials is the more complex option, justified mainly if separate deployment/scaugmentaling of frontend and backend is wanted.
- Overkill: dynamically computing CORS per-request from a broad allowlist/regex "in case origins change later" for a single, fixed personal deployment — a fixed, explicit origin string is simpler and safer.

### Gaps
- Did not fetch the underlying `expressjs/cors` or `@fastify/cors` package READMEs directly for the full options list (e.g., `optionsSuccessStatus`, `maxAge`); NestJS's docs link to them but weren't separately fetched. For implementation, consult those linked READMEs for the exact option names.

## Reverse proxy / hosting and HTTP security headers

### Takeaway
Terminate TLS at the proxy (Cloudflare/Nginx/Caddy/hosting LB), forward the real client IP so NestJS's rate limiter and logs see the correct origin, and set the standard protective headers (CSP, HSTS, X-Content-Type-Options, X-Frame-Options/CSP frame-ancestors, Referrer-Policy) — NestJS 12.1+'s `app.useSecurityHeaders()` sets sane defaults for most of these in one call with no extra dependency.

### Cited Findings
- NestJS: `app.useSecurityHeaders()` ("Starting with NestJS v12.1... uses the same defaults as Helmet 8") sets, by default: `Content-Security-Policy` (a default policy), `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Origin-Agent-Cluster: ?1`, `Referrer-Policy: no-referrer`, `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `X-Content-Type-Options: nosniff`, `X-DNS-Prefetch-Control: off`, `X-Download-Options: noopen`, `X-Frame-Options: SAMEORIGIN`, `X-Permitted-Cross-Domain-Policies: none`, `X-XSS-Protection: 0`, and removes `X-Powered-By` — all headers apply to route responses, 404s, error responses, CSRF-rejected responses, and SSE streams — [NestJS Security headers docs](https://docs.nestjs.com/security/helmet).
- Must call `useSecurityHeaders()` (and `enableCsrfProtection()`) "before `app.init()` or `app.listen()`," and right after `NestFactory.create()` so no earlier middleware bypasses the headers — [NestJS Security headers docs](https://docs.nestjs.com/security/helmet), [NestJS CSRF docs](https://docs.nestjs.com/security/csrf).
- OWASP HTTP Headers Cheat Sheet: prefer the CSP `frame-ancestors` directive over `X-Frame-Options` where supported ("CSP frame-ancestors directive obsoletes X-Frame-Options for supporting browsers"); recommend `X-Frame-Options: DENY` to block framing entirely; explicitly recommend turning off `X-XSS-Protection` (`X-XSS-Protection: 0`) rather than enabling it, since the legacy XSS auditor it controls can itself introduce vulnerabilities; set `X-Content-Type-Options: nosniff`; and set `Referrer-Policy` explicitly (e.g., `strict-origin-when-cross-origin`) rather than relying on browser defaults — [OWASP HTTP Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html).
- NestJS rate-limiting docs: behind a reverse proxy, configure `app.set('trust proxy', 'loopback')` (or the appropriate trusted-proxy value) on the Express adapter so `X-Forwarded-For` is honored correctly for per-IP throttling — [NestJS Rate Limiting — Proxies](https://docs.nestjs.com/security/rate-limiting).

### Inferences
- Essential and nearly free: call `app.useSecurityHeaders()` immediately after creating the Nest app (before any other middleware), which covers almost the entire OWASP HTTP Headers checklist in one line on NestJS ≥ 12.1 (older Nest versions should use the `helmet` npm package directly, which provides the same defaults).
- Essential for the proxy layer itself: terminate TLS at the proxy with a valid certificate (e.g., automatic via Cloudflare or Let's Encrypt/Caddy), redirect all HTTP to HTTPS, and ensure the `Strict-Transport-Security` header is actually sent (it's ignored over plain HTTP per MDN/OWASP, so HTTPS must be enforced first) and forward `X-Forwarded-For`/`X-Forwarded-Proto` correctly with `trust proxy` configured app-side.
- Nuance, not overkill but worth tuning: the default CSP from `useSecurityHeaders()`/Helmet 8 is a generic baseline; a single-page React app usually needs a custom, tightened CSP (e.g., restricting `script-src`/`connect-src` to the app's own origin and only the exact third-party endpoints actually used) rather than relying purely on defaults — this is a deliberate configuration step at implementation time, not something to skip.

### Gaps
- Did not fetch the exact default CSP policy string NestJS's `useSecurityHeaders()`/Helmet 8 applies (the table referenced "See Content Security Policy" sub-section which wasn't fetched in full); implementers should view that sub-section or Helmet 8's own CSP defaults before finalizing the CSP for the React app's actual script/style/connect sources.

## Production validation and ongoing privacy considerations

### Takeaway
Beyond initial implementation, validate the deployed app against the concrete header/cookie/CSRF/CORS checklist above using live browser devtools + an external scanner, keep dependencies patched, log and monitor authentication events (without logging secrets), and apply basic data-minimization/privacy hygiene even for a one-user app (since the deployment is public-facing and may still process the owner's personal data).

### Cited Findings
- OWASP's layered guidance across the fetched cheat sheets repeatedly ties correctness to *verification*, not just configuration: e.g., CSRF cheat sheet's advice to "Implement at least one mitigation from Defense in Depth Mitigations" and to test built-in protections before assuming they work — [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
- Credential-stuffing cheat sheet's "Defense in Depth & Metrics" section: "each defense should generate volume metrics for use as a detective mechanism... Monitoring and reporting on these metrics may identify defense failures or the presence of unidentified attacks" — i.e., logging/alerting on auth failures is itself a named control, not just a nice-to-have — [OWASP Credential Stuffing Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html).
- NestJS's security-header/CSRF docs both emphasize that headers/CSRF checks apply to *all* response types including error/404 responses and must be registered before other middleware — a concrete, testable configuration fact (e.g., verify via an actual request that a middleware added earlier via `app.use()` isn't bypassing the protections) — [NestJS Security headers docs](https://docs.nestjs.com/security/helmet), [NestJS CSRF docs](https://docs.nestjs.com/security/csrf).

### Inferences
- Practical production validation checklist implied by the above sources: (1) hit the deployed site with browser devtools and confirm `Set-Cookie` shows `HttpOnly; Secure; SameSite=...` and no `Domain` leaking to subdomains; (2) confirm HSTS/CSP/X-Content-Type-Options/X-Frame-Options are present on a real response (including an intentionally triggered 404/error) to catch middleware-ordering mistakes; (3) attempt a crafted cross-origin `fetch()` from a throwaway origin to confirm CORS/CSRF actually reject it; (4) confirm the login endpoint's rate limit triggers after the configured attempt count from a single IP, and that the real client IP (not the proxy IP) is what's counted; (5) confirm TLS redirect and certificate validity; (6) run an automated header/TLS scan (e.g., Mozilla Observatory-style or `curl -I` checks) as a cheap sanity pass.
- Privacy, scoped to proportion: since this is a one-user personal app, heavy "privacy program" machinery (DPIAs, cookie-consent banners for third-party tracking, etc.) is overkill unless the app itself embeds third-party trackers/analytics; the essential privacy controls are the security controls already listed (don't log passwords/secrets/session tokens in plaintext logs, encrypt backups, restrict DB/network access) plus not adding any third-party analytics/trackers the owner doesn't need, which keeps privacy obligations minimal by design.
- Keep NestJS, its auth-related packages (`@nestjs/throttler`, passport strategies, cookie/session libraries), and the password-hashing library current, since OWASP repeatedly ties session/password-storage recommendations to "the latest version available, that potentially fixes all the well-known vulnerabilities" of built-in framework session/auth mechanisms — [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

### Gaps
- No single authoritative OWASP "production deployment checklist" page was fetched in this research pass (e.g., the OWASP Application Security Verification Standard or a dedicated deployment cheat sheet); the checklist above is synthesized/inferred from the per-topic cheat sheets rather than quoted from one canonical deployment-validation source. A follow-up search for the "OWASP Testing Guide" authentication-testing chapter or ASVS V2/V3 (authentication/session management) controls would make this section more directly citable if deeper validation detail is needed.
